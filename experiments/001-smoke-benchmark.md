## تجربة 001: فحص أولي لحلقة الجمع

- التاريخ: 2026-10-10
- الإصدار: سُدى 0.2.0
- الجهاز: Windows 10، معمارية AMD64؛ طراز المعالج وسعة RAM غير مسجلين
- Python: CPython 3.14.8
- الأمر: `python benchmarks\benchmark.py --items 100 --rounds 3 --warmup 1`
- الفرضية: تنفيذ حلقة bytecode في VM Python-hosted أبطأ من حلقة Python مباشرة.
- إعداد الخوارزمية: حلقة جمع متسلسلة على المجال `0..99` في الطرفين؛ الترجمة
  مستبعدة من عينات steady-state، مع تسجيل زمن الترجمة منفصلًا.
- تحقق الناتج: كلا التنفيذين أعادا 4950.
- VM سُدى: وسيط 0.0012383 ثانية، متوسط 0.0013182 ثانية،
  انحراف معياري 0.0001528 ثانية، أعلى عينة (p95 لعينة صغيرة جدًا)
  0.0014943 ثانية.
- Python: وسيط 0.0000080 ثانية، متوسط 0.0000088 ثانية،
  انحراف معياري 0.0000015 ثانية، أعلى عينة 0.0000105 ثانية.
- زمن الترجمة المقاس: 0.0004247 ثانية.
- `tracemalloc` لعينة واحدة: VM 6171 بايت، Python 0 بايت مرصودًا.
- الطاقة وحرارة الجهاز وذروة RAM للعملية: لم تُقَس.
- التفسير: في هذا الاختبار الصغير وعلى هذا التشغيل، VM أبطأ بوضوح؛ النتيجة
  لا تمثل تطبيقات عامة ولا تقيس backend أصليًا. صفر `tracemalloc` في حلقة
  Python يعني أنه لم يرصد تخصيصًا متزامنًا أثناء تلك العينة، لا أن العملية
  لا تستخدم ذاكرة.
- القيد: ثلاث عينات غير كافية لاستنتاج موثوق أو فاصل ثقة؛ طراز CPU وحالة
  الحرارة غير مسجلين، واستبعاد compiler مقصود للـ steady-state.
- القرار التالي: استخدم `--rounds 30` أو أكثر، إدخالًا أكبر، وثّق طراز CPU
  وحالة الطاقة والحرارة، وقِس RAM للعملية بأداة النظام عند تقييمات الأداء.
